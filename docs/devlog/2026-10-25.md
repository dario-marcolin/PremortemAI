## 1. Phase 4 – Web search tool

Branch: `phase-4/web-search-tool`

### Files

- `premortem/tools/web_search.py`: `@tool web_search(query)` wrapping `TavilySearch`.
  - Returns at most `MAX_SEARCH_RESULTS` results, each with only `title`, `url` and `snippet` (cut at 500 characters).
  - Errors are returned as data (`[{"error": ...}]`), never raised: missing key, API exception, no results, unexpected response. The LLM can then rephrase and retry.
  - The docstring is the tool's prompt. It says when to use the tool (facts the document does not give), how to phrase queries (category and country, with an example) and what it returns.
- `tests/test_web_search.py`: 7 offline tests with a fake Tavily client, plus 1 live test that is skipped without `TAVILY_API_KEY`.

### Manual test: 3 queries about the demo product (task for C)

| Query | Result quality |
|---|---|
| `plant-based protein crisps competitors France` | Relevant to the category but **global**: 5 market-report vendors (Persistence, Future Market Insights, Mordor, Grand View...). Global brands only (General Mills, Optimum Nutrition, Myprotein), no French brand such as Gerblé. |
| `protein snacks market size France` | Partly **off target**: 2 of 5 results are about protein *ingredients*, not protein snacks. |
| `French consumer trends protein snacks Nutri-Score` | **Good**: French sources (Santé publique France, a PMC paper, NielsenIQ/Kantar coverage). |

What this changed in the Analyst prompt: brand-level queries instead of "competitors", market-report pages treated as weak evidence, and the document's own figures kept as the main source for segment sizes.

### Free-tier usage (task for A)

- Tavily plan: Researcher (free), **1,000 credits per month**. One basic search = 1 credit. Usage can be checked with `GET https://api.tavily.com/usage`.
- Measured in Phase 5: one Analyst run uses **7 to 8 searches**, so the free tier covers about **125 full runs a month**. That is enough for Phase 10, but tuning runs count too.

## 2. Phase 5 – Analyst subgraph

Branches: `phase-5/analyst-prompt` (prompts, task for B) → `phase-5/analyst-subgraph` (code, task for A)

### Design decisions

1. **Two LLM steps.** First, a ReAct loop (`analyst_llm` ⇄ `tools`) researches the market. Then one `analyst_report` call turns the document and a plain-text **research log** into the `Analysis`. The report call does not get the tool-call history, only the log as text.
2. **Bounded loop without errors.** The loop is capped at `MAX_TOOL_ROUNDS = 6`, derived from `ANALYST_RECURSION_LIMIT = 15`. At the cap the graph goes to the report instead of raising `GraphRecursionError`, so a long search still produces an analysis.
3. **Sources are checked in code, not trusted from the LLM** (`normalize_sources`):
   - sources are renumbered `S1, S2...`, document first, then web;
   - a web source whose URL never appeared in a search result is removed (invented URL);
   - citations to unknown ids, and sources that nothing cites, are removed;
   - every removal is written in `data_quality_notes`, and the ids cited inside text fields (e.g. "480M euros [S2]") are renumbered too.
4. **Extensible tools.** `get_analyst_tools()` returns `[web_search]`. It is the only place where the bonus tools (customer data, market sizing) will be added.

### Files

- `premortem/prompts/analyst.md`: research step. Role, procedure (read brief and document first, then search), brand-level queries, about 6 searches, no invented figures, small segments reported as they are.
- `premortem/prompts/analyst_report.md`: report step. Source numbering, one document source per section, one competitor per brand, a source id on every need and figure. It has one good competitor example and one good segment example about a different product (an oat drink in Germany), so the demo answers do not leak into the prompt.
- `premortem/agents/analyst.py`: `get_analyst_tools()`, `build_analyst()`, the three nodes, `normalize_sources`.
- `tests/test_analyst.py`: 6 offline tests (fake LLM): loop, cap, invented URL, renumbering, unknown citations.
- `tests/run_analyst.py`: live run, see section 7.

### Hand check: competitors, URLs, figures (task for C)

- Every figure cited in run 1 (380M euros, +443%, 70–75 euros/kg, 2.20 euros per bar, 43.3 g, 65%) appears in the research log: **no invented numbers**.
- Every cited URL comes from Tavily. Most open directly. carrefour.fr (403), barebells.fr and minceurdiscount.com (429) block scripts, but the pages are real.
- **The trap is reported correctly in every run:** vegans are 1.3M adults, 2.5% of adults, 72% intent.
- Competitors are real brands (Barebells, Gerblé, private labels, IronMaxx, Minceur Discount...). The analysis also notes that Gerblé and Barebells sell no protein crisps in France, which is useful for positioning.

**Problems found and fixed**

1. *Three brands grouped in one competitor* (run 1). Prompt: one entry per brand.
2. *Five document sections in one source, plus a duplicate* (run 1). Prompt: one source per section.
3. *Customer needs without a source id.* Prompt: every need ends with `[Sx]`.
4. *Code: ids in `data_quality_notes` were not renumbered, and uncited sources were kept.* Fixed in `normalize_sources`.
5. *Code: a real source was removed because the LLM dropped `www.` from the URL.* URLs are now compared without scheme, `www.` and trailing slash, and the exact URL from the search is kept.

**Still open (now reported by the judge, see Phase 7)**

- Haiku sometimes still merges several document sections into one source (run 4).
- IronMaxx is cited with German and Slovenian shop pages (.de, .si), not French ones.

### Cost and limits

- One run costs about 62–70k tokens with Haiku (mostly input, because the document is sent in every turn), 7–8 searches and about 50 seconds.
- The tool-round cap was never reached (at most 3 of 6 rounds), so the limit does not need to be lowered.

## 3. Phase 6 – Strategist and Creative

Branch: `phase-6/strategist-creative`

### Design decisions

1. **The Strategist sees the brief and the analysis, not the raw document.** Every claim in the strategy therefore goes through the analysis sources, which the validator can check.
2. **Targeting compares segments on size, interest, accessibility, competition and fit with goals**, and reads size and interest together. The trap is not hard-coded anywhere.
3. **Shared revision logic** (`premortem/agents/revision.py`). A node revises when the latest validation of its own stage has blocking issues, or, for the Strategist only, when `human_feedback` is set. The previous output, all issues of that validation and the feedback are added to the prompt ("Revise the strategy. ..."), and the revision counter (`strategy_revisions` / `campaign_revisions`) is increased by one. Warnings alone do not trigger a revision.
4. **Language.** The strategy and the campaign concept, content ideas and visual direction are in English, for the team. The tagline and the messages are in the language of the target country.

### Files

- `premortem/prompts/strategist.md` (task for B): STP procedure. The target id and the source ids must exist in the analysis. Channels are short names that the campaign must reuse exactly. Includes how to handle validation issues and human feedback.
- `premortem/prompts/creative.md` (task for B): at least one message per strategy channel and no other channels. Claims only from the brief or the strategy, no comparative claims, no promises of body effects.
- `premortem/agents/strategist.py`, `premortem/agents/creative.py`: nodes with `with_structured_output(Strategy)` / `(Campaign)`. The Creative also receives the target segment.
- `tests/test_strategist_creative.py`: 6 offline tests on the revision logic, using `dummy_state.json`.
- `tests/run_strategist_creative.py`: live chain on a saved Analysis, with an optional human rejection, see section 7.

### Runs (saved Analysis from Phase 5 run 4, Haiku 5.5)

| Run | Target | Channels | Deterministic checks |

| 1 | SEG2 Weekly sport practitioners (17.5M, 34%) | 5 | all pass |
| 2 (after prompt fix) | SEG2 | 4 | all pass |

- The trap is avoided: the rationale compares about 7.2M interested sport practitioners with about 0.94M interested vegans, against the goals of 1,500 points of sale and a 2% share.
- After the human feedback, the Strategist follows the company and writes the risk, with figures, in the rationale.

### Marketing check (task for B and C)

**Problems found in run 1 and fixed in the prompts**

1. *Comparative claim* "Plus de protéines que les chips protéinées habituelles". It came from the +30% claim, which the analysis flags as measured in Italy only. Now the Strategist uses only claims not flagged in `data_quality_notes`, and the Creative makes no comparative claims.
2. *Tagline* "Le croquant qui vous muscle". It promised a body effect and contradicted the concept. Claims must now stay factual and the tagline must express the positioning. Run 2: "Croquant. Protéiné. Tout simplement."
3. *Supermarkets and Hypermarkets as separate channels*, with almost the same message. The prompt now says to merge such channels. Haiku follows this only sometimes; the judge reports it.

**To decide (B and C)**

- Flavour names stay in English ("Sea Salt", "Rosemary") inside the French copy. Are they brand names, or should they be translated?
- The positioning statement sometimes uses internal wording ("the unverified protein chips of IronMaxx"). That is fine for the team, but it must not reach the copy.

About 20k tokens and 24 seconds per Strategist + Creative chain with Haiku. A rejection adds one Strategist call: about 30k tokens and 29 seconds in total.

## 4. Phase 7 – Validator

Branches: `phase-7/validator-rules` (rules, task for A) → `phase-7/validator-judge` (judge and validator node, tasks for B and A)

### Design decisions

1. **Rules first, then the judge.** `make_validator(stage)` runs the deterministic rules, then the LLM judge, and appends one `ValidationResult` to `validations`. When a rule already blocks (e.g. the target segment does not exist), the judge is skipped, because its review would be meaningless.
2. **The judge must quote its evidence, and the code checks the quote.** Each judge issue gives the `field` it relies on and an exact `quote` of it. A blocking issue whose quote is not in the input (case and spaces ignored) is **downgraded to a warning**, so an objection that cannot be traced never sends a stage back.
3. **Analysis issues are always warnings**, as in the roadmap: the graph never loops back to the Analyst.
4. **The rubric says exactly when an item is blocking.** Everything else is a warning ("when in doubt, warning"). Style, wording and missing caveats are never blocking.
5. **The judge sees the company document**, not only the brief. Without it, the judge treated the company's own product facts (e.g. "no palm oil") as unsupported.

### Files

- `premortem/validation/rules.py`: the 7 rules of the To-Do List.
  - Analysis: every competitor and segment has a source; every source id exists (warnings).
  - Strategy: the target segment exists and every supporting source exists (blocking); the target segment has an `estimated_size` (warning).
  - Campaign: every message channel is in the strategy (blocking); every channel has a message (warning).
- `tests/test_rules.py`: one passing and one failing case per rule (11 tests).
- `premortem/prompts/judge.md`: one rubric per stage, with an id per item (e.g. `segment_size_and_access`, `claims_supported`, `distinct_channels`).
- `premortem/validation/judge.py`: `judge(stage, state)`, with the quote check.
- `premortem/agents/validator.py`: `make_validator(stage)`.
- `tests/fixtures/small_segment_case.json` (task for C): the "small segment" case. It holds the real Phase 5 Analysis, a hand-written strategy that targets vegans (SEG1, 2.5%) on enthusiasm alone, and the Phase 6 SEG2 strategy as a control.
- `tests/test_validator.py`: 7 offline tests (fake judge).
- `tests/run_judge.py`: live run of every case, twice, see section 7.

The rules alone pass every Phase 5 and 6 output, **including the vegan strategy**: the id exists and the sources are valid. Catching a bad choice is the judge's job.

### Judge temperature and model (task for B)

- The To-Do List asks for a low judge temperature (e.g. 0). **Claude 5 models reject `temperature`** (error 400, "temperature is deprecated for this model"). The optional setting `LLM_JUDGE_TEMPERATURE` exists for other providers and is empty by default. Instead, stability was checked by running every case twice.
- **Haiku 5.5 is not reliable as a judge.** Over three prompt versions every fix moved the error somewhere else. It blocked the good strategy, let "Le croquant qui vous muscle" pass, and wrote issues that said "no problem here".
- **Sonnet 5.5, with the same prompt: 10 of 10 verdicts correct, and the same verdict in both runs of every case.**

| Case | Expected | Haiku (final prompt) | Sonnet (2 runs) |
|---|---|---|---|
| Analysis | warnings only | ✔ | ✔ ✔ |
| Strategy SEG1 vegans (trap) | blocking `segment_size_and_access` | ✔ | ✔ ✔ |
| Strategy SEG2 (control) | pass | ✔ | ✔ ✔ |
| Campaign with "qui vous muscle" and a comparative headline | blocking `claims_supported` | ✘ passed | ✔ ✔ |
| Campaign after the Phase 6 fix | pass | ✘ blocked | ✔ ✔ |

**Decision:** the judge has its own model, set by `LLM_JUDGE_MODEL` (Sonnet 5.5), while the agents stay on `LLM_MODEL` (Haiku for development). A judge call takes about 12 seconds with Sonnet, against 4 with Haiku. With Sonnet, the judge also notes that the vegan strategy leaves out supermarkets (68% of sales), and it quotes the figures.

The open points of Phases 5 and 6 are now reported by the judge as warnings: `source_quality` (sources from another country, merged document sections) and `distinct_channels` (supermarkets vs hypermarkets).

```
main ← phase-1/schemas-state ← phase-2/ingestion ← phase-4/web-search-tool

     ← phase-6/strategist-creative ← phase-7/validator-rules ← phase-7/validator-judge
```

- This differs from the rule agreed on 23 October ("avoid stacking branches"). It was chosen because nothing could be merged in the meantime. Since the stack is a single line with no merge commits, it stays easy to bring into `main`.
- `phase-4/web-search-tool` was first created from `main`, then rebased onto `phase-2/ingestion` to keep the line straight. It was not pushed before the rebase, so no force push was needed.
- Branch names follow the To-Do List (e.g. `phase-4/web-search-tool`, not `phase-4/web-search`).
- Every branch is pushed. No PR is open for Phases 4 to 7 yet.

**How to merge the stack into `main`**

- Merge in order: PR #1, PR #2, then one PR per branch, each based on the previous branch.
- With "Squash and merge" (our default), the next branch must be rebased after each merge: `git rebase --onto main <previous-branch> <branch>`. Alternatively, use "Rebase and merge" for this stack. That keeps the commits and needs no rebase.
