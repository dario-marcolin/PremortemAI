## 2. Design decisions

1. **Both systems are scored the same way, from their output folder.** The metrics read `blueprint.md` and `run.json` and nothing from inside the pipeline. The baseline is asked for the same outline and the same citation format (`[n]` and a Sources list), so the comparison measures the architecture (tools, validator, specialised agents), not the format.
2. **What is scored.** The plan without the validation log and the sources list. The judge never sees the validation log: it would tell it which system wrote the plan.
3. **Traceability.** The judge (Sonnet) extracts the factual claims about market, competitors, customers and segments, with their `[n]`. Claims about the company itself are left out, because both systems copy them from the document. Following the same idea as the Phase 7 judge, the code checks what the LLM returns:
   - a claim counts only if its quote is in the plan;
   - a reference counts only if it is cited on the same line.

   **Valid source:** the company document, or a URL that exists. A page that refuses bots (403) counts as valid; a 404 or an unknown domain does not. A reference with no URL (e.g. "Nielsen 2024") is not valid, because nobody can check it.
4. **Faithfulness.** No LLM. Each figure of the claims is searched in the document and in the pages of the URLs the claim cites (fetched over HTTP).
   - The search handles "1.3 million" vs "1,276,000", decimal commas ("1,3 million") and ranges.
   - Rounding is accepted up to 3% of the figure. Without that cap, "10 million units" matched the document's "9.6 million" (a false positive found in the first live run).
   - *Unverifiable* means a cited page exists but cannot be read. Unverifiable figures are listed but left out of the score.
5. **Coherence and trap: one judge call** with a fixed rubric (`eval/prompts/coherence.md`). It returns two scores (strategy vs analysis, campaign vs strategy), each with a reason, plus the primary target and whether it is the trap segment. The fields are flat, because nested objects came back incomplete from Sonnet in the first live run. A malformed answer is retried once.
6. **Cost and latency** come from `run.json`: tokens of every model, and pipeline seconds (human wait excluded). The evaluation's own judge calls (about 20k Sonnet tokens per plan) are saved in `metrics.json` but not counted.
7. **Failures do not stop the evaluation.** A failed run or evaluation is recorded and shown in the report as "failed: …". The averages only cover the cases where **both** systems finished, so a failed run (0 tokens) cannot pull them down. `--cases <id>` re-runs one case and keeps the others in `eval/results.json`.
8. **Blind rating (`eval/rating/`).**
   - Each pair is labelled X/Y at random; the mapping is in `key.json`, which raters must not open.
   - The multi-agent blueprint loses its validation log and its "Approved by the company" line, so the format does not give it away. The title becomes "Launch plan: <case>" for both plans.
   - The pairs are not rewritten once ratings exist.
   - 5 questions: usefulness, evidence, target, coherence, clarity.
   - `--report-only` adds the averages to the report, plus the plans where raters disagree by 2 points or more.

## 3. UI: the Evaluation tab

- **At the end of a run**, the blueprint is evaluated automatically under a spinner ("Evaluating the blueprint: claims, figures, coherence…") and saved to `outputs/<run_id>/metrics.json`. The sidebar toggle *Evaluate the result* turns this off; the tab then shows an *Evaluate this run* button.
- **Tiles:** traceability, faithfulness, the two coherence scores, tokens, pipeline time. Under them: the judge's reasons and, for an eval case, a badge "trap avoided" or "trap segment targeted".
- **Expanders:** claims (with their references and whether they are traced), figures (where each was found), sources (status of each URL).
- ***Compare with the single-prompt baseline*** runs the baseline on the same document (`outputs/<run_id>/baseline/`), scores it, and adds the difference under each tile ("+8 pts vs single prompt"). The baseline plan can be read in an expander.
- An evaluation error is shown in the tab; the blueprint and the other tabs stay available.

### What this first case shows (not yet the findings: one case only)

- **On the demo, the baseline does as well as the pipeline on every quality metric, for 8× fewer tokens and half the time.** It even avoided the trap: it used vegans as advocates, not as the target.
- **The demo cannot separate the two systems on evidence.** All the market and segment figures are in the document, so the baseline simply cites the document; its 8 sources are all document sections. The pipeline's added value (web research, figures checked against real pages) cannot show when there is nothing to research.
- **Proposal: add one or two cases with gaps.** For example, a document with no market size and no competitor list, where a plan must either research or invent. This is where the baseline is most likely to invent figures or cite sources that do not exist. Now a priority: see section 7.
- **The multi-agent loses traceability on its executive summary.** By design (Phase 9) the summary has no references, and the extractor counted 3 of its claims as untraced. This is a real weakness for a reader who only reads the summary. Options:
  - allow references in the summary;
  - make the extractor skip claims repeated from cited sections (it already should: "keep the occurrence that cites a reference").
- Only one run per system and case, so this is anecdotal: wait for the other cases and for the human rating.

## 6. How to check it by hand

```bash
uv run pytest tests/test_eval.py tests/test_app.py -v               # offline
uv run python -m eval.run_eval --cases demo_fr                       # one case, both systems (~3 min)
uv run python -m eval.run_eval --report-only                         # rebuild the report
uv run streamlit run app.py                                          # run the demo, open the Evaluation tab
```

Check in the report:
- every case has a row per system;
- the targets in "Details per case" match `state.json` → `strategy.target_segment_id`;
- open one `metrics.json` and check that 2–3 "not found" figures are really absent from the document.

Cost of a full evaluation run (5 cases):
- about 105k Haiku tokens per pipeline run and 13k per baseline;
- plus about 20k Sonnet tokens per plan evaluated (×10 plans);
- about 15–20 minutes.

## 7. Priorities after Phase 10: the expansions

Decision (30 Oct): the tie on the demo was expected. When the document already holds all the data, one prompt can summarise it well. The advantage of the multi-agent system should come from the **expansions** (roadmap section 6), which become the priority after v1.

**Rule for every expansion:** it comes with an eval case and a metric that can show its advantage over the single prompt. Otherwise we only measure another tie.

| Priority | Expansion (roadmap) | Why one prompt cannot do it | Eval case and metric |
|---|---|---|---|
| 1 | **Initial company data through a RAG system** (6.1, documents path: chunk, embed, vector store, `search_company_docs` tool) | Today the whole document goes into the prompt, up to `DOC_TOKEN_BUDGET` (60k tokens). With several long documents (reports, past plans, survey results), one prompt must cut or skim them and loses the details | A case with several documents, together above the budget; traceability to the exact document and passage, and faithfulness on figures from the passages |
| 2 | **Customer data: tables through analysis tools** (6.1, tables path: `profile_customers`, `segment_customers`, `compare_segments`) | It cannot count, average or cluster thousands of rows, so it estimates and invents | A case with a customer CSV; the figures of the plan are checked against values computed in code from the CSV |
| 3 | **Research when the document has gaps** (6.9 better web search, 6.3 market sizing) | Without the figures in the document, it invents them or cites sources that do not exist | A "gap" case: no market size, no competitor list; traceability and URL checks |
| 4 | **Pricing** (6.8, and the 29 Oct bonus idea: `price_search` tool) | It does not know real shelf prices; it guesses them | Faithfulness on prices against the cited pages |
| 5 | **Revision after feedback** (v1 feature, to be measured) | It rewrites the whole plan, including what the company already approved | Reject with a feedback, then measure what changes besides what was asked |

Also to add to the evaluation, with no expansion needed:
- **Stability** answers the "reusable" part of the research question, which is not measured yet.
- How: run each system 3 times on the same case. Does it keep the same target and the same figures?
- We expect the structured state and the validator to make the pipeline more stable than one prompt, but this must be checked.

Order: first complete today's run on the 5 cases as the v1 baseline. Then add the "gap" case (3), which needs no new code, then the RAG system (1) and the customer tables (2). The hooks are already in v1:
- `get_analyst_tools()`;
