## 1. Design decisions

1. **The Analyst subgraph is added as a node directly** (`g.add_node("analyst", build_analyst())`). It shares `brief`, `document_text` and `analysis` with `LaunchState`; its `messages` stay inside the subgraph (checked by the smoke test).
2. **Routing** (`route_strategy`, `route_campaign`): `"revise"` only if the *latest* validation of the stage has blocking issues **and** the counter is below `MAX_REVISIONS`. Warnings never loop.
3. **Unresolved issues are carried forward.** At the limit the graph goes on: the blocking issues stay in `validations`, the approval step shows them with `unresolved: true`, and the CLI warns when the campaign ends with blocking issues. Phase 9 will list them in the blueprint.
4. **Human approval** (`human_approval`): `interrupt()` with the strategy, the issues of its latest validation, `unresolved` and the revision count. Resume with `Command(resume={"approved": bool, "feedback": str})`. A rejection with no text uses a default feedback, so the Strategist always gets a reason.
5. **Checkpointer:** `MemorySaver` with an explicit allowlist of our Pydantic models. Without it, LangGraph 1.2 warns "Deserializing unregistered type" at every resume and will block it in a future version.
6. `blueprint` is a no-op placeholder until Phase 9.

### Change to Phase 6 code: human feedback and the revision counter

This answers the open question of the 25 October log (point 8.5).

- **Before:** the Strategist cleared `human_feedback` after using it. In the graph, the strategy judge (which reads the feedback) and any validator-driven revision after a rejection no longer saw it. Example: "target vegans" → Strategist picks SEG1 → judge blocks on size without knowing the company asked for it → the revision, with no feedback, could go back to SEG2 and silently override the company.
- **Now:** `human_feedback` stays in the state from the rejection until the next approval (`human_approval` clears it). `human_approval` resets `strategy_revisions` to 0 on a rejection. The Strategist increments the counter only when it answers blocking issues.
- **Consequence:** after a rejection, the validation loop has a fresh budget. If the human rejects a strategy that still had unresolved blocking issues, the first revision answers both the feedback and those issues, so it counts as revision 1.
- Two Phase 6 tests were updated to the new rule (`test_strategist_revises_on_human_feedback`, `test_strategist_keeps_feedback_in_validator_revisions`).

## 3. How to check it by hand

Prerequisite: `.env` with `LLM_API_KEY`, `TAVILY_API_KEY`, `LLM_JUDGE_MODEL=anthropic:claude-sonnet-5-5`.

**Offline tests first (free, ~3 seconds):**

```bash
uv run pytest tests/test_graph_smoke.py tests/test_graph.py -v
```

**Run 1 – approve directly (task C).** Interactive: answer `y` at the prompt.

```bash
uv run python scripts/run_cli.py --doc data/demo/demo_company.pdf
```

Check: one line per node in this order: `extract_brief`, `analyst` (with its searches), `validate_analysis`, `strategist`, `validate_strategy`, then the approval screen; after `y`, `creative`, `validate_campaign`, `blueprint`. A folder `outputs/<run_id>/` with `state.json` and `run.json`.

**Run 2 – reject with feedback (task B).** At the prompt, type the feedback directly (or `n`, then the feedback), e.g. `Focus on gym-goers and sport shops`.

Check:
- the next lines are `human_approval rejected`, `strategist`, `validate_strategy`, then a second approval screen;
- the new strategy follows the feedback (target, channels, or the risk written in the rationale);
- `run.json` → `decisions` has the rejection with your text, then the approval;
- `state.json` → `human_feedback` is `null` at the end.

**Run 3 – force a revision loop (task C).** Ask for the trap segment, which the judge blocks on evidence:

```bash
uv run python scripts/run_cli.py --doc data/demo/demo_company.pdf --reject "Target vegans only (SEG1)"
```

`--reject` rejects the first strategy with that text, then asks you as usual (answer `y`).

Check:
- after the rejection, `strategist` / `validate_strategy FAILED` repeat, and the loop **stops after 2 revisions** (`revisions: 2` on the last strategist line);
- the second approval screen says "Blocking issues are still unresolved: the revision limit was reached" and lists `judge.segment_size_and_access`;
- the Strategist kept the company's request (SEG1) and stated the risk in the rationale, instead of going back to SEG2.

The segment ids depend on the analysis of that run: check the segment list in `state.json` → `analysis.segments` if SEG1 is not the vegan group.

Cost per run (Haiku agents, Sonnet judge): about 70k Haiku tokens + 35k Sonnet tokens, 7–8 Tavily searches, 1.5 minutes. Each extra revision adds one Strategist call and one judge call.

## 7. Phase 9 – Launch Blueprint

Branch: `phase-9/blueprint`

### Outline (task for C)

As in the To-Do List: 1 Executive summary, 2 Company brief (with missing information), 3 Market and competitors, 4 Segments (table), 5 Strategy, 6 Campaign, 7 Validation log, 8 Sources. Two additions:

- A **callout under the summary** when blocking issues are still unresolved (revision limit reached), so nobody acts on the plan without seeing them.
- **Data gaps and assumptions** (the analysis `data_quality_notes`) at the end of section 4, next to the figures they qualify.

### Design decisions

1. **Rendered from the state.** Only the executive summary is written by an LLM. Every other value comes from the state through `templates/blueprint.md.j2`, so the blueprint cannot drift from what the agents decided.
2. **Numbered references.** Source ids become `[1]`, `[2]`... in order of first appearance, both in source lists and inside text ("1.3M adults, S1" → "1.3M adults [1]"). An unknown id is kept and marked (`[S9?]`) rather than hidden. Sources the blueprint never cites are still listed at the end.
3. **Validation log.** Every `ValidationResult` in run order ("Strategy, check 2: failed"), each issue marked `blocking, resolved`, `blocking, unresolved` or `warning`. A blocking issue is resolved when the latest validation of its stage no longer raises the same check as blocking.
4. **Where the file goes.** The state has no blueprint field (frozen contract), so the `blueprint` node writes the file: `outputs/<thread_id>/blueprint.md`. The CLI now uses the run id as the thread id, so `blueprint.md`, `state.json` and `run.json` are in the same folder. New setting `config.OUTPUT_DIR`.
5. **The summary cannot break the run.** If the LLM call fails, the blueprint is saved with a note in place of the summary.
6. **PDF export: skipped.** It was optional ("only if quick"); `weasyprint` needs system libraries that are not installed. Markdown only for now; the Streamlit UI (Phase 11) can offer the download.

## 8. Phase 11 (minimal) before Phase 10 – Streamlit UI

Branch: `phase-11/ui` (stacked on `phase-9/blueprint`)

### Why the order changed

Decision (Dario, 29 Oct): build a **minimal** UI first, then the evaluation on top of it. The two phases do not depend on each other (the evaluation runs headless with auto-approve), and the UI makes it fast to try new documents, including the eval cases of 10.1, while watching what each agent does. Risk: the evaluation answers the research question, the UI does not, so the UI was kept to the essentials (polish only after Phase 10). **To align with the team:** the order in the To-Do List and in the roadmap.

### Design decisions

1. **One shared runner, `premortem/runner.py`.** The `Run` class holds the compiled graph, the thread (`thread_id` = run id), the log and the run record. `advance()` streams until the approval pause, the end or an error, yielding one `LogLine` per step; `answer()` resumes with `Command(resume=...)`. The CLI, the UI and (next) `eval/run_eval.py` all use it, so the log and the saved files are the same everywhere.
2. **`log.txt` in every run folder**, written line by line as the run goes, with the traceback if a node fails. The Analyst's searches and their result counts are logged too.
3. **Errors do not lose the run.** A failing node is logged, `run.json` is saved with `status: failed`, and Retry (UI) continues from the last checkpoint: the brief and the analysis are not redone.
4. **Two small changes to the CLI output.** `seconds` in `run.json` is now pipeline time, without the time the human spends at the approval prompt (better for Phase 10 latency). `run.json` also gets `status` and `error`. Tokens are now counted with a callback in the run config instead of a context manager, because the UI resumes the graph in a later script execution.
5. **Streamlit reruns.** The `Run` lives in `st.session_state`. The run streams inside one script execution and the page is redrawn after each log line. If a click cuts the stream short, the next execution continues from the last checkpoint.
6. **Progress panel: no `st.status`.** The To-Do List suggests it, but Streamlit does not allow an expander inside an `st.status`, and the Analyst's searches need one. The panel is a plain log (time, step, result) with the searches folded in an expander. The status line under the title and the pipeline track above the panels show where the run is.
7. **Look.** Styled with the `design-taste-frontend` skill (app-screen rules, style "achromatic ledger"): ink on an off-white ground, near-black primary button, one colour (blue) only on the running step, Geist font. Theme in `.streamlit/config.toml`, a few CSS rules in `app.py`.
